# 5. Alembic for schema migrations, UUID primary keys

Date: 2026-09-22
Status: Accepted

## Context

The database schema will change over the life of the project (new tables, new
columns, new indexes), and those changes must be applied safely and repeatably
across local, staging and production environments.

## Decision

- Use Alembic for all schema changes. No table is ever created by calling
  `Base.metadata.create_all()`; every table exists because a migration created it.
- Every table uses a UUID primary key generated by Postgres (`gen_random_uuid()`),
  not an auto-incrementing integer.
- `created_at` / `updated_at` are set by Postgres via `server_default`, not by
  application code.
- A shared naming convention is applied to all constraints and indexes up front.

## Consequences

- Schema history is explicit, reviewable in pull requests, and reversible.
- IDs are safe to expose in URLs and API responses; they don't leak row counts or
  creation order.
- Correctness of timestamps and ID generation doesn't depend on which process or
  language inserts a row.
- Slightly more ceremony per table (write a migration) than an ORM's auto-create,
  which is the trade-off we accept for a production-shaped project.
